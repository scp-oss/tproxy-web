# Быстрый деплой — с чего начать

Сначала выберите сценарий — он определяет, какой `docker-compose*.yml` и какие флаги
`init.sh` вам нужны. Все три сценария используют один и тот же код (`relay` + `tgws`),
разница только в том, кто перед ними стоит и терминирует TLS.

| У вас есть... | Сценарий | Файл |
|---|---|---|
| NPM (Nginx Proxy Manager) работает в Docker на ЭТОМ ЖЕ сервере | [NPM на этом сервере](QUICKSTART-local-npm.md) | `docker-compose.yml` |
| Главный NPM на ДРУГОМ сервере, но вы его администрируете (можете прописать Proxy Host и IP-фильтр) | [Удалённый NPM под вашим управлением](QUICKSTART-remote-npm.md) | `docker-compose.remote-cf.yml` |
| NPM чужой/внешний (хостинг-провайдер, другой админ) — максимум, что можно получить, это один Proxy Host. Либо NPM вообще нет, и у вас просто есть IP:порт | [Чужой NPM или без NPM](QUICKSTART-no-npm.md) | `docker-compose.remote-cf-caddy.yml` |
| Голый VPS: домен указывает ПРЯМО на сервер, никакого NPM/CDN/веб-сервера перед ним нет вообще | [Голый VPS, из коробки](QUICKSTART-vps-out-of-the-box.md) | `docker-compose.remote-cf-caddy.yml` + `CADDY_AUTO_HTTPS=1` |

Не уверены — берите последний вариант («Чужой NPM или без NPM»): он работает всегда,
просто у него на один внешний прыжок больше (какой-то ваш локальный веб-сервер — Caddy, nginx,
Apache, не важно какой), если вы администрируете NPM сами — можно сразу пойти по среднему
варианту и сэкономить этот прыжок.

В каждом сценарии распаковка проекта + `sudo ./install.sh` — это ВСЁ, что нужно сделать на
этом сервере: `install.sh` без аргументов открывает меню, спрашивает только то, что нужно для
выбранного варианта (домен, при необходимости IP NPM или домен Cloudflare Worker'а), сам
вызывает `init.sh` с правильными флагами и поднимает нужный `docker-compose*.yml`. Единственный
шаг, который скрипт сделать не может — настройка снаружи (NPM или веб-сервер), он у каждого
сценария свой, см. соответствующий QUICKSTART-*.md.

Файл называется `docker-compose.remote-cf-caddy.yml` по имени рекомендуемого по умолчанию
варианта (Caddy — проще всего настроить с готовым сертификатом), но сам режим работает с
любым локальным веб-сервером — примеры блоков для Caddy/nginx/Apache есть в
[QUICKSTART-no-npm.md](QUICKSTART-no-npm.md).

## Общее для всех трёх сценариев

- Протокол **WEB-прокси жёстко требует порт 443** на стороне клиента — в ссылке
  `https://t.me/webproxy?server=...&secret=...` параметра порта нет. Чем бы вы ни пользовались
  (NPM, Caddy, что угодно) — порт 443 должен в итоге привести именно к вашему `relay`.
- `install.sh`/`init.sh` идемпотентны: повторный запуск с теми же (или без) флагами не
  меняет уже созданные секрет, base path, ключ подписи токенов и выбранный `--carrier`. Можно
  спокойно перезапускать после правки флагов.
- Секрет и ссылка клиента печатаются один раз при первом запуске `init.sh`. Чтобы увидеть их
  снова без смены секрета — просто запустите `init.sh` ещё раз с теми же `--hostname`
  (и остальными флагами режима).
- Все режимы одинаково поддерживают выход в Telegram через `tg-ws-proxy` (прямой WebSocket +
  запасной путь через ваш Cloudflare Worker) — шаги настройки Worker'а общие, см.
  [QUICKSTART-cloudflare-worker.md](QUICKSTART-cloudflare-worker.md).
- Полное описание всех граблей, найденных при реальном деплое (Docker NAT на loopback,
  провайдерские файрволы, баг с `dd`-префиксом секрета и т. д.) — в README.md, разделы
  «Решённые проблемы» и «Режим: бэкенд за чужим/внешним NPM».
